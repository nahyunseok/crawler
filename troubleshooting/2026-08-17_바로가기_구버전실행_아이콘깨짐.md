# 배포 후 사고: 바탕화면 바로가기가 구버전을 실행하고 아이콘이 깨짐

- **발생일:** 2026-08-17 (v1.0.16 릴리스 직후)
- **증상 신고:** "바탕화면 아이콘이 제대로 반영이 안 된 것 같다. 그리고 버전이 1.0.16인데 대시보드에는 1.0.15로 표시된다."

---

## 1. 증상

| 증상 | 사용자가 본 것 |
|---|---|
| ① 버전 표시 불일치 | `version.txt` 는 1.0.16 인데 프로그램 화면 좌측 하단에 `v1.0.15` |
| ② 아이콘 미반영 | 바탕화면 바로가기가 프로그램 아이콘이 아닌 기본 아이콘으로 보임 |

## 2. 진짜 원인 (두 증상은 같은 뿌리)

바탕화면 바로가기(`Gemini 이미지 수집기 V2.0.lnk`)가 **v1.0.16 을 전혀 가리키고 있지 않았다.**

```
대상    : D:\Users\user\Claude-Workspace\crawler\dist\Gemini_Image_Crawler_v1.0.15\Gemini_Image_Crawler_v1.0.15.exe  ← 살아있음
아이콘  : C:\Users\user\Claude-Workspace\crawler\app_icon.ico                                                        ← 존재하지 않음
```

### ① 버전이 1.0.15 로 보인 이유
프로젝트 폴더를 `D:\Users\user\Claude-Workspace\crawler` → `C:\Users\user\Desktop\crawler` 로
**"옮겼다"고 생각했지만 실제로는 복사**였고, 옛 폴더가 D드라이브에 그대로 남아 있었다.
바로가기는 옛 폴더의 v1.0.15 exe 를 계속 실행했고, 그 exe 안에 번들된 `version.txt` 는 `1.0.15` 였다.

> **즉 신버전 코드는 한 줄도 실행되지 않고 있었다.** 새로 빌드한 exe 자체는 정상이었다
> (`dist/Gemini_Image_Crawler_v1.0.16/_internal/version.txt` = `1.0.16` 확인).
> `main.py` 의 `get_version()` / `resource_path()` 는 문제가 없었다.

### ② 아이콘이 안 나온 이유
바로가기의 아이콘 경로가 **대상 exe 와 다른 파일**(프로젝트 루트의 `app_icon.ico`)을 가리켰고,
그 경로가 C드라이브(존재하지 않음)로 박혀 있었다. 파일이 없으니 윈도우가 아이콘을 그리지 못했다.

- 대상은 `D:\`, 아이콘은 `C:\` 로 서로 다른 드라이브인 이유:
  바로가기를 만들 당시 `C:\Users\user\Claude-Workspace` 가 D드라이브로 향하는 **정션(junction)** 이었다.
  `WScript.Shell` 은 `TargetPath` 는 실제 경로(D:)로 정규화해 저장하지만,
  `IconLocation` 은 **문자열 그대로**(C:) 보존한다. 나중에 그 정션이 사라져 아이콘 경로만 깨졌다.

### ③ 왜 이런 바로가기가 만들어졌나 — `build.py` 의 설계 결함
```powershell
$targetPath = Join-Path $PWD 'dist\...\x.exe'      # ← 실행 시점의 '현재 폴더' 기준
$shortcut.IconLocation = Join-Path $PWD 'app_icon.ico'   # ← 대상과 다른 파일
```
- `$PWD` 는 **bat 을 어디서 호출했는지**에 따라 달라진다. 정션 경로를 경유하면 그 경로가 박힌다.
- 아이콘을 대상 exe 와 다른 파일로 지정하면, exe 는 살아있는데 아이콘만 깨지는 상태가 만들어진다.

### ④ 함께 발견된 상품성 결함 (고객 영향 — 더 심각)
배포 zip 에는 **exe 하나만** 들어 있었다.
`바로가기_만들기.bat` 과 `app_icon.ico` 는 프로젝트 루트에만 있어 zip 에 포함되지 않았다.
→ 고객은 **바로가기를 만들 방법도, 매뉴얼도 받지 못했다.** (전역수칙 7 '바로가기 자동 생성·매뉴얼 포함' 위반)
게다가 bat 이 프로젝트 루트의 `app_icon.ico` 를 참조하므로, 고객 PC 에서는 애초에 성공할 수 없었다.

## 3. 해결책

### 즉시 조치
- 바탕화면 바로가기를 v1.0.16 exe 로 재생성, 아이콘은 **exe 자체**(`exe,0`)에서 가져오도록 변경
- `ie4uinit.exe -show` 로 윈도우 아이콘 캐시 갱신

### 재발 방지 — `build.py` 수정 (⛔ 수정금지 주석으로 의도 고정)
| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| 경로 기준 | `$PWD` (호출 시점 현재 폴더) | `pushd "%~dp0"` — **bat 자기 위치** |
| 아이콘 원본 | 프로젝트 루트 `app_icon.ico` | **대상 exe 자체** (`$target,0`) |
| exe 없을 때 | 깨진 바로가기를 조용히 생성 | 사유를 알리고 **생성하지 않음** + 종료코드 전달 |
| zip 동봉물 | exe 하나 | exe + `바로가기_만들기.bat` + `MANUAL.md` + `CHANGELOG.md` |
| 빌드 실패 | `print` 만 하고 **종료코드 0** (성공처럼 보임) | `sys.exit(1)` |

**핵심 원칙:** 아이콘 원본을 대상 exe 와 **같은 파일**로 두면, 대상이 유효한데 아이콘만 깨지는
상태가 구조적으로 불가능해진다. (대상이 없으면 실행도 안 되므로 항상 일관됨)

### 검증 방법 (재현 절차)
1. 생성된 bat 을 **프로젝트와 무관한 폴더**(`C:\Windows`)에서 호출 → 바로가기 경로가 정확한지 확인
2. exe 가 없는 상황 → 종료코드 ≠ 0, 깨진 바로가기가 생성되지 않는지 확인

두 경우 모두 통과 확인함.

## 4. 남은 정리 대상 (사용자 확인 필요)

- `D:\Users\user\Claude-Workspace\crawler` — 옛 프로젝트 폴더가 그대로 남아 있다.
  구버전 exe(v1.0.5~v1.0.15)와 옛 `.spec` 11개, 빌드 잔재가 들어 있고,
  **이번 혼란의 직접 원인**이므로 정리하는 것이 좋다. (임의 삭제하지 않음)

## 5. 교훈

- **"버전이 안 바뀐다"는 신고는 코드가 아니라 '무엇을 실행 중인가'를 먼저 의심할 것.**
  이번에도 `get_version()` 코드는 처음부터 정상이었다.
- 폴더를 옮겼다면 **바로가기·작업 스케줄러·다른 스크립트가 옛 경로를 참조하는지** 함께 확인해야 한다.
- 배포판 zip 은 항상 **"고객이 이 zip 만 받았을 때 필요한 게 다 들어있나"** 기준으로 검사할 것.
  개발자 PC 에는 있는 파일이 고객에게는 없다.
